# Dagrs Harness 核心引擎計畫（2026-09-26）

## 文件職責

本計畫將 Dagrs 從靜態／半靜態 FBP 任務圖執行器，演進為可供外層 Harness 驅動模型回合、工具呼叫、審批與子 Agent 的執行及持久化核心。交付重點是穩定的 State、super-step、Run control、interrupt、事件、checkpoint、動態派送與 child-run 契約，並以 provider-neutral 的 Harness 範例驗證。

本計畫不把 Dagrs 改成完整 Agent SDK。模型供應商、prompt、tokenizer、MCP client、IDE/TUI、CRI 與 sandbox 的具體實作留在外層；Dagrs 提供調度、狀態、策略掛接及恢復所需的通用原語。

### 適用範圍

- `dagrs` crate：共享 State 與 Reducer、super-step 執行、deadline/cancellation/budget、interrupt/resume、事件流、逐步 checkpoint、動態 operation dispatch、child run、retry 與 policy hook。
- `dagrs-derive`：只在新 State／節點宣告 API 確實需要 derive 支援時同步修改；不可為了本計畫預先擴大 macro 語義。
- 以通用 `OperationRuntime` / `ToolRuntime` 邊界連接外層；在 `examples/agent-harness/` 用 fake model 與 fake tools 示範閉環。
- 同步根 `README.md`、`dagrs-derive/README.md`（僅 macro 有變更時）及 `docs/CHANGELOG.md`；新增針對 checkpoint、interrupt、dynamic dispatch 和 child run 的測試。

### 非目標

- 在 Dagrs 中實作模型 SDK、prompt 模板、tokenizer、MCP client、provider-specific tool-call parser 或 Agent UI。
- 在 Dagrs 中實作容器 runtime、CRI/youki、網路隔離或 OS sandbox。核心只提供可檢查的副作用宣告與 policy hook；實際隔離由外層執行器負責。
- 把 `libscheduler` 的 filter/score/bind 語義或 rk8s garbage-collector owner-ref graph 合併進 Dagrs Graph。
- 允許執行中的既有圖任意改寫任意節點與邊。本計畫採取有界、可持久化的 step-level 動態派送；既有靜態子圖仍可使用 DAG/FBP。
- 直接修改 rk8s monorepo。提供的缺口報告未附 rk8s commit SHA，實際 CSI／Pod 整合列為延後項，須在獨立整合計畫中 pin revision。
- 本計畫內向 crates.io 發布或推送 release artifact；只做 API、版本策略與 package readiness 收口。

### 成功定義

- 外層可用同一個 serializable、可宣告讀寫範圍的 State，跨 super-step 執行模型決策、並行工具批次與觀察結果；state reducer 的衝突處理具決定性。
- 呼叫端可設定 deadline、協作式取消與步數／時間／自訂用量預算；任務可在操作前掛起等待 approve、deny 或修改後再從同一 step 恢復。
- 每個 step 的狀態、待執行 operation、事件游標及 checkpoint 可持久化；可列出 thread 歷史、從 checkpoint fork，並以 cursor replay 執行事件。
- Harness 可動態派送一批 operation，並 spawn/join 有獨立 checkpoint、預算上限和 isolate/fork context 的 child run。
- 核心提供 retry、能力宣告、pre/post policy hook、artifact reference 與 context middleware 擴充點；不宣稱這些 hook 本身就是 OS sandbox。
- `examples/agent-harness/` 以 fake `ModelRuntime` 和 fake `ToolRuntime` 完成可測試的 model → operation batch → observe → next turn 閉環，且 Dagrs 核心不依賴模型供應商套件。
- 全部必要任務與適用驗收通過；完成時不宣稱 rk8s 已整合，除非後續 pinned-revision 整合計畫已完成。

## 已決議設計決策

### ADR-DAGRS-HC-01：Dagrs 是 Harness 執行核心，不是完整 Agent SDK

- **狀態：** `Accepted`
- **背景：** 模型、prompt、tokenizer、MCP、UI、CRI 與 sandbox 有不同生命週期和相依；塞進核心會讓 DAG runtime 與供應商／平台耦合。
- **決策：** Dagrs 負責 graph/runtime、shared state、step、動態派送、checkpoint、事件與 policy extension point。Agent loop、ModelRuntime、工具協議轉換、上下文壓縮、真實 sandbox 與 UI 留在外層。例子用 trait 與 fake runtime 示範，不引入 provider SDK。
- **考慮過的方案：** 把 `AgentNode`、prompt、MCP client 一起納入 Dagrs；拒絕，因為會把模型協議和外部工具生命週期固定成核心依賴。
- **影響：** 引擎需提供能承載開放 loop 的 state、step、dynamic send、interrupt 和 child run 契約，但不直接執行模型請求。
- **重新評估條件：** 至少兩個獨立外部 Harness 對同一核心 API 有相同需求時，才評估是否抽取獨立 adapter crate。

### ADR-DAGRS-HC-02：在 super-step 邊界以 Reducer 提交共享 State

- **狀態：** `Accepted`
- **背景：** 並行節點若任意修改同一個會話上下文，恢復與 replay 會受完成順序影響。
- **決策：** 一個 super-step 內所有節點讀同一個 State revision；各自輸出帶 key 的 delta；step barrier 按明確規則 reduce 並提交下一 revision。提供具型別的 key 包裝及 serde/schema 邊界；`append`、`overwrite`、`sum` 和自訂 reducer 都需有可驗證衝突規則。
- **考慮過的方案：** 共享可變 HashMap；拒絕，因為多 writer 狀態和 checkpoint replay 不穩定。以每條 channel 複製整份 messages；拒絕，因為會重複序列化大型上下文。
- **影響：** 現有 `EnvVar` / `Content` 與靜態 Graph 先保持可用；Harness API 走新增的 RunState/step 契約，完成相容性評估前不刪舊介面。
- **重新評估條件：** 真實 workload 顯示 barrier 延遲或 State encoding 成為瓶頸時，以 benchmark 比較增量 state 或分區 reducer。

### ADR-DAGRS-HC-03：只在 step 邊界動態派送，不任意熱改正在執行的圖

- **狀態：** `Accepted`
- **背景：** 模型每輪可產生新 operation，但任意改寫既有拓撲會使 checkpoint、節點識別和重播難以定義。
- **決策：** 保留靜態 Graph 作為可重用子流程；step 完成後可提交有穩定 ID 的 `Send` / operation batch 或 child run，這些派送項會先持久化再執行，並受 budget、concurrency 和 policy 限制。
- **考慮過的方案：** 執行中直接 `add_node/add_edge`；拒絕，因為很難定義與 checkpoint 的一致性。所有模型 tool call 都在 compile 時預先展開；拒絕，因為不支援開放 loop。
- **影響：** 不改變「靜態 DAG 可用」；dynamic run 有獨立的 persisted scheduler state 和操作收據。
- **重新評估條件：** 多個使用案例確實需要 mid-step topology mutation，且其 checkpoint/replay 語義已由獨立設計證明時。

### ADR-DAGRS-HC-04：外部副作用採可恢復的至少一次語義

- **狀態：** `Accepted`
- **背景：** 引擎在遠端工具已完成但本地 checkpoint 尚未落盤時崩潰，無法只靠本地狀態保證 exactly-once。
- **決策：** 每個 operation 有穩定 idempotency key、持久化的 pending/started/result 狀態及明確 retry policy。外部 ToolRuntime 應支援冪等或查詢既有結果；不支援時恢復流程必須暴露 `outcome_unknown`，不可假裝未執行。
- **考慮過的方案：** 宣稱 transaction 跨本地 checkpoint 與任意外部工具；拒絕，因為工具端不參與同一交易。
- **影響：** Human gate 會在 operation 開始前持久化批准決策；恢復時使用同一 operation ID，必要時先 reconcile 再重試。
- **重新評估條件：** 外部 operation backend 提供可驗證的交易或冪等保證時，可縮小 reconcile 流程。

## 全局工程約束

- **GC-01 現況先行：** 開工時刷新當前 API、錯誤碼、測試 targets、feature 與行號；未 pin 的外部文件不得作為實作真相。
- **GC-02 核心邊界：** Dagrs 只定義 provider-neutral runtime contracts。Model SDK、prompt、tokenizer、MCP、IDE/UI、CRI 和實際 sandbox 不進 `dagrs` 核心依賴。
- **GC-03 舊 API 遷移：** 對 `Graph`、`Node`、`Action`、`EnvVar`、`Content`、checkpoint 和 `dagrs-derive` 的既有呼叫端做 source compatibility 評估；不能靜默改變語義。
- **GC-04 Reducer 決定性：** 一個 super-step 的讀取 revision 固定；寫入 reducer、衝突、錯誤與 commit 順序必須明文定義並可重播。
- **GC-05 副作用至少一次：** 本地 checkpoint 不能替任意遠端 side effect 提供 exactly-once。必須有穩定 operation ID/idempotency key；結果未知時傳回可恢復錯誤狀態。
- **GC-06 協作式取消：** deadline/cancel 不可只 abort task 而遺失資源清理、checkpoint 或 operation 狀態；明確定義取消傳播與超時後的 drain 策略。
- **GC-07 Budget 來源：** 核心可計算 step、wall-clock、併發和外部 meter 回報值；token 和金額由外層 model adapter 報量，Dagrs 不含 tokenizer 或計價表。
- **GC-08 Policy 不等於 sandbox：** `OperationSpec` 和 hook 只對經由 Dagrs operation dispatcher 的呼叫做授權／審核；任意 Rust Node 仍可做外部 side effect。文件不可宣稱核心完成 OS、網路或容器隔離。
- **GC-09 Checkpoint schema：** thread、run、step、State、pending operation、approval、child lineage、retry 和 event cursor 都需有版本化序列化與舊格式相容策略。
- **GC-10 事件順序與隱私：** 執行事件有 run/thread/step/sequence/schema version；事件內容不得默認存入 prompt、token、secret 或完整個人資料，需明確 redaction 與 retention。
- **GC-11 有界資源：** child、operation、broadcast、事件歷史、checkpoint 與 artifact 保留皆有容量/並行上限及清理語義。
- **GC-12 錯誤處理：** 新失敗沿用 `DagrsError` / `ErrorCode`，區分取消、deadline、budget、policy、interrupt、retry exhausted 和 outcome unknown；生產路徑不得新增無解釋 panic。
- **GC-13 Cargo 相依：** SQLite/Xline/object store 等具體後端依賴留在 adapter 或 optional crate；核心不能為單一部署綁定 rk8s 或 provider runtime。

### 故障恢復矩陣

| 故障情境 | 可接受狀態 | 恢復動作 | 不可接受結果 |
|---|---|---|---|
| Run 在 State delta reduce 前崩潰 | 舊 revision 完整 | 從上一 checkpoint 重做尚未 commit 的 step | 部分 key 寫入或讀到半個 revision |
| RunStore commit 中途崩潰 | step/state/events/dispatch 全部舊或全部新 | 原子交易/outbox recovery 後查詢 commit ID | checkpoint 已前進但 operation/event journal 遺失 |
| tool 已完成但結果未持久化 | `outcome_unknown` + 固定 idempotency key | 先由 adapter reconcile，再記 receipt 或明確要求人工處理 | 無提示重跑破壞性操作或宣稱 exactly-once |
| 等待 approval 時進程重啟 | interrupt record 保留 | cursor 載入 pending request，採唯一決策 ID 恢復 | 從頭重跑前置模型/工具並重複副作用 |
| child run 超時／失敗 | child 狀態可查，parent 按 join policy 決定 | 取消或收集其餘 child，parent 記錄 partial result | child 寫入污染 parent State 或留下無限背景 task |
| Artifact 被清理但仍有 checkpoint ref | 不允許刪除 | GC 依引用計數/保留期重試 | resume 遇到靜默缺檔或 digest mismatch 未報錯 |

## 風險登記

| 風險 | 可能影響 | 緩解／偵測方式 | 任務 |
|---|---|---|---|
| State/reducer 對外 API 過早固定 | 後續多 Harness 無法表達 typed keys 或 conflict semantics | 先測定 shared-step API，保留 custom reducer trait，版本收口前 API review | HCE-01、12 |
| 任意 tool side effect 無法 exactly-once | 崩潰恢復重複寫檔、shell 或付費 API | operation receipt、idempotency key、unknown outcome、reconcile contract | HCE-04..06 |
| cancellation 只 abort Rust future，外部 process 仍繼續 | 資源洩漏、重複執行、狀態與實際效果分歧 | Cooperative cancel + adapter process handle cleanup，加入 timeout/failure injection | HCE-02、06 |
| event/checkpoint 記錄 prompt 或 secret | 資料外洩及歷史無限增長 | payload redaction、namespace policy、retention/cursor GC、合成 fixtures | HCE-03..05 |
| 動態 child fan-out 無上限 | CPU/memory/GPU/費用耗盡 | inherited budgets、max concurrency、spawn quota、join timeout | HCE-02、07 |
| Checkpoint 新 schema 無法降版讀取 | 舊程式重啟後無法恢復 | schema version、legacy fixtures、明示 downgrade policy | HCE-04、12 |
| Policy metadata 被誤認為沙箱 | 執行任意 Node 的外層誤以為已隔離 | API docs 明示只保護經 dispatcher operation；真實限制由 sandbox/runtime 實施 | HCE-09、11 |
| rk8s integration report 對應版本不明 | 計畫落在錯誤的 CSI/Pod API | 未 pin SHA 前不接觸外部 source；另開整合計畫 | DEFER-01 |

## 效能與容量摘要

| 操作 | 成本或增長來源 | 預算／上限 | 驗證方式 |
